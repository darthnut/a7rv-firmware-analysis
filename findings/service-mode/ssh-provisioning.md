# SSH provisioning — how service mode stands up `sshd`

**Summary.** `libInfraSSHManager.so` is the a15-side service that starts/stops `sshd`, provisions the
login as a `crypt(3)` `$5$` SHA-256 hash file, and generates/persists the ECDSA host key through the
Backup store — all driven by numbered OSAL commands, with `sshd` launched by posting a command *string*
to an executor task rather than any libc `exec`.

**Where.** `fs/a15/lib/libInfraSSHManager.so` (project `ghidra_svc`; VA = file offset + `0x100000`).
Dispatcher `doMsgReceiptProcess` `0x10a9b8`; `executeStartSshdCmd` `0x109e30` → `startSshd` `0x10908c` →
`executeIMSystem` `0x108ed8`; key path `createKeyFromBackup` `0x10885c`, `updateBackupKey` `0x1097e8`,
`deleteBackupKey` `0x1089a4`; credentials `executeSetAuthInfoCmd` `0x10a534`, `encryptPassword`
`0x10820c`, `makeSalt` `0x108178`, `updatePasswordFile` `0x108318`; PAM `resetPamFailureCount` `0x109124`.

**Mechanism.**
- **Verb surface:** request ids `0x1000000x` → response `0x2000000x` (start/stop sshd, set auth info,
  delete host key, notify cam-remote, reset PAM tally; register/unregister notify events `0x3000000x`).
- **How a command runs:** `executeIMSystem` posts the command string to OSAL endpoint **`0x94020a`**
  (message type `0x940023`, 256-byte buffer) and reads the exit code from the reply — **no
  `system`/`popen`/`fork`/`exec` imports exist**. The five commands it can cause to run: `/usr/sbin/sshd`,
  `/bin/busybox killall sshd`, `/usr/bin/create_host_key.sh`, `/usr/bin/get_finger_print.sh`,
  `/sbin/pam_tally2 --reset -u <user>`.
- **Gating:** `executeStartSshdCmd` requires `isKeyValid()` (host key present → result `5` if not) and is
  idempotent (`isSshdStarted()` → result `0`). SET_AUTH_INFO is refused while sshd runs.
- **Host key:** generated by `create_host_key.sh` (ECDSA, inferred from path names) only when auth info
  is first set or on credential rotation; **persisted in the Backup store** as item `0x3000000`
  (subsystem `0x300`) and rewritten to tmpfs (`/tmp_network/ssh/ssh_host_ecdsa_key`, mode `0600`) at
  every init — so it survives reboot despite living on tmpfs.
- **Login credential:** `crypt(3)` **`$5$` (SHA-256), `rounds=5000`, random 16-char salt**, written as
  `user,hash` under `flock` to `/tmp_network/ssh/ssh_name_password`. Not a Unix user, not
  `authorized_keys`; consumed by sshd's PAM path (the `pam_tally2` machinery confirms PAM is in the loop).

**Verification.** *light (strings/imports), but many bodies decompiled.* ~35 functions decompiled by
address; the request↔response id pairing confirmed from the dispatcher switch *and* the controller
vtable; the exec-via-OSAL mechanism confirmed by the empty process-creation import set; the `$5$`
hashing read from clean callee bodies.

**Boundary / open.** Endpoint `0x94020a`'s owner (`libSTMcmdexecute.so`, which shells the string out) is
a NEEDED dependency not decompiled — **HYPOTHESIS**. The key *type* (ECDSA) is inferred from path
constants; the generator script was not read. sshd's own PAM config (which maps the password file to
logins) is outside this binary. A noted robustness caveat: the username is concatenated **unescaped**
into the `pam_tally2` command string — exploitability depends on the executor's shell semantics
(unexamined). What a remote client does *over* the session is out of scope.
