# Sony a7R V firmware — consolidated static analysis

A synthesis of 21 subsystem studies of the author's **own** Sony a7R V (ILCE-7RM5) firmware,
produced by a local reverse-engineering pipeline and verified against the binaries. Each section
cites the per-subsystem document in this folder. Offsets and mechanism are documented; no key
material or firmware bytes are reproduced.

**Method.** Static analysis only, in Ghidra (headless, by-address decompilation to avoid PLT
thunks) plus `nm`/`strings`/byte reads, across the extracted a15 (AArch64 Linux) side and the
cpapp / av-cam main-SoC images. Every load-bearing claim was spot-checked against the binary by a
separate verification pass; claims that could not be confirmed statically are marked **HYPOTHESIS**
and the boundary is recorded rather than guessed past. Images in hand: cpapp-b.bin (17.6 MB),
av-cam.bin (13 MB), and the a15 `fs` (352 shared objects, 75 service ELFs). The main-SoC-side and
hardware roots are **out of image** and are called out as such.

---

## 1. The crypto / keystore spine

The camera's data-at-rest protection is a four-layer stack, now traced end to end up to the point
where it leaves the extracted firmware.

**SecVault (`libsecvlt.so`)** — a secure store of **four fixed slots** selected by a 32-bit item
magic (descriptor table at `0x101c30`, byte-verified). Each record is a `0x58`-byte header plus
ciphertext: magic `SECVAULT` (`DEADDEAD` after delete), a **wrapped data-encryption key (DEK)** at
`+0x08`, a cleartext 12-byte IV, the GCM tag, size, and attributes. Encryption is **AES-256-GCM**
via OpenSSL EVP (`FUN_00100f4c`). Slot 2 is **unreadable by design** (an attribute bit makes
`SECVLT_load` refuse it forever). *(secvault-map.md, secvaultslots-map.md)*

**Key handling (keywrap-map.md).** On store, the DEK is **per-record random** (`RAND_bytes`, 32
bytes). On load, the DEK is filled entirely by an RPC **response payload** — it is unwrapped by an
out-of-process key service. The **key-encryption key (KEK) never enters `libsecvlt.so`**. This is
the definitive static boundary: the master key lives provider-side (the key service or hardware),
not in any extracted a15 image.

**Key service (keyservice-map.md).** SecVault and the Backup store both reach the crypto service
at **OSAL QID `0x25906be`** (module `0x0259`, slot `0x06be`, kernel-routed). The command protocol
is `2 = import-key → opaque handle`, `3 = crypt`, `5 = release`; `0x428`-byte messages, `0x400`-byte
chunks, direction fixed at import. The provider is **not in any loaded image** (the QID is built in
code, found by zero raw-byte sweeps); the strongest candidate is `libsecvlt.so` itself acting as
the SECVAULT front end, but who owns the QID server is unresolved — **HYPOTHESIS**.

**Persistence (backup-map.md, below).** SecVault records persist through the Backup store, keyed by
`(subsystem, item)`.

**Net picture:** application data → SecVault (AES-256-GCM, random per-record DEK) → Backup store →
backup daemon; the DEK is wrapped by a KEK held in an out-of-image key service. Confidentiality of
everything at rest reduces to that one provider-side key.

## 2. Service mode (factory / maintenance channel)

**Authentication → dispatcher → verbs → shell**, now mapped as a chain.

- **Authentication** (prior work, Investigation 2): a 3-level SHA-256 challenge-response in
  `libsencore.so`, ending in sshd provisioning.
- **Dispatcher (sencatalog-map.md).** The real post-auth verb dispatcher is in **`libsencore.so`**,
  not the `sen.elf` daemon. Chain: `SenserThread` `@0x10b7ac` (reads a 12-byte header; verb = u16 at
  `buf+4`) → `Parse` `@0x10e9f4` (walks the active verb table, verb → factory) → `Command::Execute`
  `@0x10db08` (**auth gate** at vtable+0x28 → status `0x82` if unauthenticated; dispatch at
  vtable+0x10) → `PluginCommand::DoExecute` `@0x10d908` (calls the handler, status → `buf[0xb]`).
  This sits one layer above the `command%04X`/`dlsym` plugin-verb resolution (plugin-verb-map.md).
- **`sen.elf` (sendaemon-map.md)** is *only* the power/lifecycle daemon (RESUME/SUSPEND on QID
  `0x3d032e`); it registers no verb table. Incidentally, the `0x8f013a` queue — an open question
  from Investigation 1 — is a **log sink** here.
- **Memory-dump verb `0xff03`** is reachable through this dispatch but returned `0x80` (locked) on
  live hardware, consistent with a missing `commandNNNN` symbol.
- **SSH provisioning (ssh-provisioning-map.md).** `libInfraSSHManager.so` starts `/usr/sbin/sshd`
  by posting the literal command string to an **OSAL command-executor** (the module imports no libc
  `exec`/`system`/`popen`). The login credential is a **crypt(3) `$5$` (SHA-256) password file**
  on the PAM path (`pam_tally2` resets confirm PAM), not a Unix user or `authorized_keys`. The
  **ECDSA host key** is generated by `create_host_key.sh` and persisted via the Backup store
  (restored at init), so it survives reboot despite living on tmpfs.

## 3. OSAL / UIPC transport (osal-uipc-map.md)

The message bus under every service command, in `libosal_uipc.so`, a userspace client of a kernel
driver at **`/dev/uipc`**.

- **Two layers chosen by QID bit 15:** set → a pure-userspace fast path (callback runs in the
  sender's thread, zero syscalls); clear → exactly one `ioctl` on the `/dev/uipc` fd.
- **ioctl ABI (independently verified by decompile of the real bodies):** `(dir<<31)|nr`, no encoded
  size — **`0x80000004` send, `0x80000005` sync-send, `0x80000008` register-callback**,
  `0x8000000a/b` alloc/free, and others. Sync-send issues the ioctl twice (request, then retire).
- **Message buffer:** `0x18`-byte header, payload at `base+0x18`, with canaries and a
  priority/flags byte.
- **Sync reply:** the kernel writes a function pointer + argument back into the request struct and
  userspace calls it — the reply is a callback, not a second message. One callback per QID.

QIDs seen across the study: `0x25906be` (key service), `0x82cd08e0` (Backup domain), `0x3d032e`
(power), `0x8f013a` (log).

## 4. Command surface

**Internal FW command table (cpappcmd-map.md).** In cpapp, `{u16 id, handler|1, flags, 0,
checker|1}` entries, **stride `0x14`**, with the **Thumb LSB** on handler/checker pointers (which is
why table-reached calls are invisible to xref analysis), and ids in **registration order, not
sorted**. 409 commands total; families decompiled:
- **Focus/drive** (cpappcmd-map.md): 8 handlers incl. `0x4152` SET_FOCUS_BRK_EXEC_STATE.
- **Exposure / metering / WB** (cmdexposure-map.md): 12 handlers (`SET_WB_MODE` `0x4006`, …), ids
  verified against the committed catalog.
- **`0x78xxxx` family** (cmdprop-map.md): **not** a GET/query layer as the catalog labels it, but a
  **change-driven property emitter** — a 150-entry dirty-flag table (`@0x10FEE4C`, bound proven two
  ways) whose handlers *push* state changes.

**Plugin verbs (plugin-verb-map.md).** Only `libpro00.so` exports verbs: `command001F` = HASP
read/reset, `command00F1` = an 8-byte success stub. Verbs resolve by `snprintf("command%04X") +
dlsym`.

**Adjustment commands (service-adjust-map.md, service-framing-map.md).** The factory tool
`adjstctl` maps **1,779** commands to `block/code` opcodes via a 72-byte record table; the send
framing and the name→opcode lookup are decompiled (and corrected an earlier off-by-4).

**External USB / PC-Remote (usbptp-map.md).** The PTP responder is **not** in cpapp/av-cam; it is in
a15 userspace: `usbg_stillimage.ko` → `libInfraPtpControl.so` → **`libInfraRemote.so`** (a singleton
`MrpwOperationsManager` with a runtime `std::map<u16 OperationCode, handler>`) over `libptp.so`. The
handler bodies are behind an un-imported library — boundary recorded. The external surface is thus a
**separate runtime opcode map**, distinct from the internal FW command table.

## 5. HASP entitlements (hasp-map.md, haspgates-map.md)

A file-backed entitlement store at `/setting/.hasp`, read/reset by plugin verb `command001F`
(`Read_Hasp`/`Reset_Hasp`, defined in both `libObj.so` and `libsencore.so`). **There are no static
HASP-id constants anywhere in the firmware** — ids arrive as runtime data through ~5 pathways — so
"which id gates which feature" is not statically resolvable; the store format is mapped, the gated
features are not.

---

## 6. Persistence / Backup store (backup-map.md, backupmap-map.md)

The persistence layer (`libBackupManager.so` → `libbkdmn.so`). A backup id is a **u32 =
(subsystem u16 << 16) | item index** (scheme proven by three decompiles). Writes build an IPC
message and send to **OSAL port `0x82cd08e0`** (the Backup domain, distinct from the key service).
Encryption is **not local** — it is the same RPC-to-key-service seen in §1 (key-handle protocol,
command 2 import / 3 crypt / 5 release). The SSH host key and SecVault records persist here. The
**per-id payload inventory is unresolved** (the payload owners are daemon-side) — **HYPOTHESIS/OPEN**.

---

## 7. Behavior: the focus-bracket write-cliff (develop-map.md)

Investigation 1 measured that focus-bracket cadence drops after ~44 frames. The firmware mechanism
is the **`ExecRcAcquire`** SDF develop-resource acquire/retry loop in `av-cam.bin` (the acquire path
is decompiled); the release side and its linkage to the write pipeline remain **HYPOTHESIS** (the
cross-chip timing is the measured part, not the static part).

---

## 8. Honest open items and static boundaries

These terminate in images or hardware not in hand, and are recorded rather than guessed:

- **The master KEK** — held by the out-of-image key service / hardware (§1). The single most
  important unresolved secret; everything at rest depends on it.
- **The key-service server** — which binary owns QID `0x25906be` is unconfirmed (candidate
  `libsecvlt.so`); HYPOTHESIS.
- **Backup payload inventory** — what each `(subsystem, item)` holds (e.g. subsystem `0x02f9`); the
  owners are backup-daemon-side.
- **SecVault slot payloads** — a prior run attributed three slots to C2PA content credentials, but
  that is **unconfirmed** (no C2PA strings in the library); treat as HYPOTHESIS.
- **PTP handler bodies** — in `libInfraRemote.so`, not imported (§4).
- **Main-SoC-side consumers** — cross-processor queue consumers and the write-cliff release side.
- **a7R VI firmware** — blocked at the crypto layer (Gen5 keys rejected); no static path without new
  key material.
